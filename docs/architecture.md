# Project architecture

The project is a Django storefront with a custom Unfold-based admin panel. The `main`
app keeps stable public imports while implementation is grouped by domain.

## Runtime

```text
django_wave_smoking/
  settings.py
  asgi.py
  wsgi.py
  urls/
    __init__.py
    admin_panel.py
    site.py
```

- The project is configured for ASGI through Daphne: `ASGI_APPLICATION = "django_wave_smoking.asgi.application"`.
- WSGI is still present for compatibility.
- The default database is PostgreSQL and is configured from `.env` values:
  `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_HOST`,
  `POSTGRES_PORT`, and `POSTGRES_CONN_MAX_AGE`.
- Local secrets and environment files are ignored by Git. Do not commit `.env` or
  `.env.example`.

Root URL configuration is intentionally ordered:

1. Admin routes from `django_wave_smoking/urls/admin_panel.py`.
2. Debug media serving when `DEBUG=True`.
3. Public site routes from `django_wave_smoking/urls/site.py`.

`main/urls/__init__.py` keeps API routes before browser routes so `/api/...` is never
captured by public catch-all routes.

## Domains

### Catalog and products

Catalog, product, review, cart, and favorite logic stays in the corresponding
`models/`, `views/`, `urls/`, template, and static feature folders.

Product media upload paths are generated by upload helpers in `main/models/__init__.py`.
Current product files should live under `MEDIA_ROOT/products/<product-id>/...`.

### Client profile

Client-card/Firebase-facing backend code lives in:

```text
main/models/client.py
main/views/client_auth.py
main/urls/api.py
```

The current backend entity is `ClientProfile`. Frontend Firebase configuration is not
kept in the repository until the auth integration is finalized.

### Warehouse

Warehouse and shipment management is a separate admin domain, not part of the
public storefront publishing flow.

```text
main/models/warehouse.py
main/admin_panel/warehouse.py
main/templates/admin_panel/warehouse/
main/static/admin_panel/warehouse/
```

Core warehouse entities:

- `WarehouseItem`: stock item linked to a product draft when needed.
- `WarehouseBatch` and `WarehouseBatchItem`: incoming batches and quantities.
- `WarehouseWriteOff` and `WarehouseWriteOffItem`: stock write-offs.
- `WarehouseCounterparty`: shipment counterparty and card number.
- `WarehouseShippingPhone`: shipping phone, PIN, active flag, and limit tracking.
- `WarehouseShipmentOrder` and `WarehouseShipmentOrderItem`: shipment requests and
  reserved/sent/returned items.
- `WarehousePointsWeekClose`: weekly points close records.

Custom admin entry points are registered through model admin URLs in
`main/admin_panel/warehouse.py`, including:

- warehouse stock page;
- incoming batch creation;
- write-off creation;
- shipment creation and status transitions;
- counterparty and shipping-phone management;
- Excel export;
- weekly points close.

Only one `WarehouseShippingPhone` should be active at a time. Shipment items reserve
stock while an order is in an active preparation state.

### Public errors and request protection

Public error handling is centralized in:

```text
main/views/errors.py
main/templates/site/errors/error_page.html
main/static/site/shared/css/site_errors.css
main/static/site/shared/js/site_errors.js
main/middleware/public_not_found_rate_limit.py
```

The public site uses a single error template for 404, 429, and 500. Error pages do
not include the public header and render as standalone full-screen pages.

`PublicNotFoundRateLimitMiddleware` limits repeated public HTML 404 requests by IP.
It excludes admin, API, static, media, favicon, and robots paths. The limit is
configured by:

```text
PUBLIC_404_RATE_LIMIT_MAX
PUBLIC_404_RATE_LIMIT_WINDOW
```

### Seamless public navigation

Public browser navigation is progressively enhanced by:

```text
main/static/site/shared/js/site_navigation.js
main/static/site/shared/css/site_navigation.css
```

Pages participating in seamless navigation must expose:

```html
<div id="site-content" class="site-content" data-site-content data-wave-page="...">
```

The navigation layer updates the document head, swaps `data-site-content`, executes
page scripts from the new content, and falls back to a styled error page when an
AJAX transition fails.

## Public routes

Browser routes live in `main/urls/site.py`:

```text
/                         home
/catalog/                 catalog
/reviews/                 reviews
/products/                product list
/products/<category>/     product list by category
/products/<id>/<slug>/    product detail
/<unmatched_path>         public 404
```

API routes live in `main/urls/api.py` and are prefixed with `/api/`.

Product detail pages are canonical by `(id, slug)`. Missing, unavailable, deleted,
or invalid products raise public 404. Wrong slugs redirect permanently to the
canonical URL.


Files under `admin/` and `unfold/helpers/` must keep their framework-defined paths.
Custom business screens belong under `admin_panel/`.

Public feature templates should keep CSS and executable JavaScript out of inline
blocks. Use feature-owned static files instead.

## Static files

```text
main/static/
  site/
    catalog/
    home/
    product_detail/
    reviews/
    shared/
  admin_panel/
    action_history/
    brands/
    categories/
    home/
    media/
    products/
    reviews/
    shared/
    variant_groups/
    warehouse/
```

Each feature owns its CSS and JavaScript. Shared components and images live in the
corresponding `shared/` directory.

Public colors and font stacks are centralized in:

```text
main/static/site/shared/css/tokens.css
```

`theme.css` and `header.css` import `tokens.css`. Public feature CSS should use
the shared tokens directly (`--bg`, `--text`, `--accent`, `--buda`, `--font-primary`,
`--font-mono`, etc.) instead of redefining local aliases such as
`--bg: var(--color-bg)`. Component-specific tokens are allowed only when they name
a real component concern, for example `--detail-accent` or `--campaign-accent`.

Admin colors and font stacks are centralized separately in:

```text
main/static/admin_panel/shared/css/admin_tokens.css
```

Custom admin feature CSS should import this file and use the shared admin tokens
directly (`--bg`, `--card`, `--border`, `--accent`, `--font`, `--mono`, etc.).
Do not duplicate full page palettes inside feature wrappers such as
`.wave-admin-products-list`; only component-specific tokens that describe a real
local concern should be introduced inside a feature file.

Generated reports such as `tools/public_css_class_audit*.json` are ignored by Git.
The `tools/run_dev.ps1` script is a project utility and may be kept under version
control.

## Media files

Runtime uploads are stored under Django `MEDIA_ROOT`, currently:

```text
media/
  products/
    <product-id>/
      main/
      variants/
      gallery/
      video/
  brands/
  warehouse/
    items/
```

The upload path is defined by model `upload_to` functions in `main/models/__init__.py`.
Product files should use product-aware names such as:

```text
products/6/main/product-6-vandal-pod-1-main-original.webp
products/6/variants/product-6-vandal-pod-1-variant-dark-night-original.webp
products/6/gallery/product-6-vandal-pod-1-gallery-01-original.webp
```

The root-level `products/` directory is legacy data from older upload experiments.
It is ignored by Git and is not used by current `MEDIA_ROOT`.
Do not add new product media there.

Image optimization belongs to Django tooling, not runtime browser code. Use:

```powershell
.venv\Scripts\python.exe manage.py optimize_images
```

By default this command is read-only and audits `media/` plus `main/static/`. Add
`--write` to write optimized files, and `--responsive` to create WebP sidecar sizes.

Node.js is not required for image processing in this project. Do not add
`package.json`, `node_modules/`, or standalone Node image tooling for product media.

## Extension rules

1. Add new public pages under `templates/site/<feature>` and `static/site/<feature>`.
2. Add new custom admin screens under `templates/admin_panel/<feature>` and
   `static/admin_panel/<feature>`.
3. Put domain models, views, and routes in the matching Python module and re-export
   public symbols from package `__init__.py` when compatibility is required.
4. Keep API routes in `main/urls/api.py`; keep browser routes in `main/urls/site.py`.
5. Keep admin-only custom screens in `main/admin_panel/<feature>.py`.
6. Do not place generated uploads, source assets, CSS, or JavaScript under
   `templates/`.
7. Do not store new user-uploaded product or warehouse images outside `MEDIA_ROOT`.
8. Do not commit local databases, dumps, backups, `.env` files, media uploads,
   generated reports, or cache directories.
